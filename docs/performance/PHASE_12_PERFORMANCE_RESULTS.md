# Phase 12 — Performance & Scale Validation

Measured on 2026-09-20. Values below are from an actual `mvn test -Pperformance` run unless marked **NOT EXECUTED**.

This phase did not change production migration behavior. Default batch size remains **10000**. No Kafka, Spark, Airflow, Kubernetes, Redis, scheduler, GUI, or cloud-specific dependencies were added. No schema changes. No speculative pipeline optimizations.

## 2. Dataset characteristics

Synthetic address-like CSV generated by `com.etp.migration.performance.BenchmarkDataGenerator`:

`record_id,house_number,street_name,street_suffix,city,state,postal_code,country,address_line_1,address_line_2,opened_on`

- Streamed to disk (bounded memory; LF newlines).
- Deterministic (record-id based; no in-memory dataset).
- Generated files are gitignored (`capabilities/etp-migration/data/` and test temp dirs).
- Mapping exercised TRIM, DIRECT, UPPERCASE, LOWERCASE, CONCAT, SPLIT, REGEX, CONDITIONAL, DATE_FORMAT.

## 3. How to run

Normal suite (performance tests excluded):

```
mvn clean test
```

Performance suite (JUnit `@Tag("performance")`, Maven profile `performance`):

```
mvn test -Pperformance
```

Optional larger e2e (gated; default profile scale is `1m`):

```
mvn test -Pperformance -Detp.migration.performance.scale=10m
mvn test -Pperformance -Detp.migration.performance.scale=30m
```

CSV-only generation (does not start Spring):

```
java -cp ... com.etp.migration.performance.BenchmarkRunner --records 1000000 --output ./data/benchmark/addresses.csv
```

`etp.migration.performance.enabled` defaults to `false` and is not used at application startup.

## 7. Multi-worker results

| Workers | Records | Batches | Wall duration | Records/sec | Staging rows | Run successRecords |
|---------|---------|---------|---------------|-------------|--------------|--------------------|
| 1 | 50k | 5 | 2.113 s | 23,663 | 50,000 | 50,000 |
| 2 | 20k | 2 | 0.390 s (later rerun 1.026 s) | 51,282 (later 19,493) | 20,000 | 20,000 or **10,000 (under-count)** |
| 4 | 40k | 4 | 0.873 s | 45,819 | 40,000 | **20,000 (under-count)** |

Observations:

- PostgreSQL `SKIP LOCKED` claimed distinct batches; all four 10k COPY operations completed (no duplicate staging at unique `(run, batch, source_record_number)`).
- Four concurrent COPY calls took ~497–521 ms each vs ~110–250 ms serial; wall clock still dropped versus four serial batches.
- Hikari snapshots after runs: control pool max 4, target pool max 4, active 0, awaiting 0. **Pool exhaustion was not observed** at 4 in-process workers.
- Concurrent `completeBatch` updates of the same `migration_run` row **lost success-counter increments** (4 batches × 10k copied, run `successRecords=20000`). Reconciliation then reported `internallyConsistent=false` / FAILED because it compares run counters to `COUNT(*)` on staging. This was **not** fixed in Phase 12 (control-plane locking change; not a throughput optimization).

## 14. Checksum

Current worker hashes the **entire source file once per batch**.

| Dataset | Checksum once | Batches | Estimated total | Share of process |
|---------|---------------|---------|-----------------|------------------|
| 50k | 4–8 ms | 5 | 40 ms | ~1.9% |
| 1M | 113 ms | 100 | 11,300 ms | **~10.9%** |

At 1M this is a **measured** cost (~11% of e2e). It was **not** redesigned in Phase 12.

Extrapolating (not measured): 10M ≈ 10× file size and 1,000 batches would make full-file checksum per batch a dominant cost. Treat that as a hypothesis until `scale=10m` is run.

## 15. Retry / restart

| Scenario | Dataset | Result |
|----------|---------|--------|
| Retry failed batch after source delete/restore | 20k / 2 batches | Staging stayed at 10k after failure; after retry+process, staging = 20k; Hikari not exhausted |
| Resume after one completed batch | 20k | Second `processAll` processed exactly 1 remaining batch; staging = 20k |
| Expired lease (`PROCESSING` + `lease_until` in the past) | 20k | Recovered via existing SKIP LOCKED lease rule; staging = 20k; recon `PASSED_WITH_WARNINGS` |
| Application process kill/restart | — | NOT EXECUTED as a separate OS-level kill (lease expiry simulated in-process instead) |

Existing Phase 7–10 ITs already cover retry/COPY replace semantics; Phase 12 confirmed them on a multi-batch synthetic file.

## 16. Bottlenecks (measured)

1. **Per-batch full-file SHA-256** — ~11% of 1M e2e; expected to worsen linearly with file size × batch count.
2. **Larger JSONB COPY payloads vs raw CSV** — isolated COPY ~90k–100k rows/sec for small maps; e2e ~9.6k records/sec at 1M includes transform, validation, checksum, claim, and COPY.
3. **Concurrent run-counter updates** — 4 workers copied 40k staging rows but persisted `successRecords=20000` (lost updates). Reconciliation against staging then fails.
4. **Error-path flushing** (observed when DATE_FORMAT config keys were wrong): persisting 10k errors/batch dominated runtime. Not a happy-path bottleneck.

## 17. Optimizations implemented

None in the production worker/connectors/checksum/COPY path.

Benchmark-only: 1 MiB `BufferedWriter` on the CSV generator; LF line endings for byte-accurate size.

## 18. Optimizations deliberately not implemented

- Caching or once-per-run source checksum
- Commons CSV replacement
- COPY → INSERT
- Default batch size change
- Hikari pool size increase
- Pessimistic locking / atomic SQL for run counters (correctness under concurrency; deferred)
- Kafka, extra queues, Spark, Airflow, Redis, Kubernetes
- GUI / scheduler

## 19. Known limitations

- 10M / 30M / 50M e2e **NOT EXECUTED**.
- 100k batch-size e2e **NOT EXECUTED**.
- OS-level JVM CPU %, PostgreSQL `pg_stat` IO, and Hikari wait histograms **NOT EXECUTED**.
- Multi-worker test uses in-process threads sharing one Spring context and one `WorkerIdentity`, not separate JVMs.
- Reconciliation checksum is warning-level for this staging target (by existing Phase 11 design).
- Surefire default includes `*Test.java` not `*IT.java`; the Phase 12 suite is named `PerformanceBenchmarkTest`.
